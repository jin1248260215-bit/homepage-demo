# 能源行业财报问答知识库（RAG）

从**巨潮资讯网**下载 15 家能源行业上市公司 FY2025 年度报告全文，解析出**带公司/章节/页码**的
正文与表格，建 **BM25 + 向量**混合索引，提供一个**答案带出处**的问答页面，并用 10 道题
（含 2 道跨公司全景题）做**逐题失败分析**。

> 这套东西的重点不是"能问答"，而是**能说清楚它什么时候答错、为什么错**。
> 评测里答错的题原样保留在 `eval/评测报告.md`，没有删。

## 数据

15 家公司，FY2025 年度报告，全部来自巨潮资讯网（`cninfo.com.cn`）公开披露。

| 板块 | 公司 |
|---|---|
| 电力（6） | 长江电力 600900、华能国际 600011、国电电力 600795、三峡能源 600905、中国核电 601985、浙能电力 600023 |
| 煤炭（3） | 中国神华 601088、陕西煤业 601225、中煤能源 601898 |
| 石油石化（3） | 中国石油 601857、中国石化 600028、中国海油 600938 |
| 新能源制造（3） | 隆基绿能 601012、宁德时代 300750、阳光电源 300274 |

年报 PDF 本身不入库（`.gitignore` 已排除 `data/pdf/`），靠 `src/download.py` 一键复现。

## 快速开始

```bash
pip install -r requirements.txt

# ⓪ 先把嵌入模型拉下来（走镜像约 12 秒）。跳过这步，第⑤步会静默卡十几分钟，见「踩过的坑」5
export HF_ENDPOINT=https://hf-mirror.com
python -c "from huggingface_hub import snapshot_download; snapshot_download('Qdrant/bge-small-zh-v1.5')"

python src/download.py        # ① 下载 15 份年报（约 46 MB）
python src/extract.py         # ② 解析：正文 + 表格，带页码/章节
python src/table_fidelity.py  # ③（可选）生成表格保真度对照报告
python src/table_audit.py     # ③'（可选）表格缺陷量化审计 → docs/table_audit.md
python src/chunk.py           # ④ 切块，挂元数据
python src/index_build.py     # ⑤ 建 BM25 + 向量索引（CPU 嵌入约 11 分钟）

python eval/run_eval.py       # ⑥ 跑 10 道评测题（含 LLM 生成）
python eval/apply_grades.py   # ⑦ 写入人工判分并重算汇总
python eval/make_report.py    # ⑧ 生成 eval/评测报告.md
python src/shoot.py           # ⑨ 起服务 + 无头 Chrome 截图 → docs/screenshots/
python src/make_delivery.py   # ⑨' 汇总交付物 → 桌面/财报问答_交付物/（副本，阅读用）
python src/app.py             # ⑩ 单独起问答页面 → http://127.0.0.1:5000
```

> 全部产出都在**本仓库这一个文件夹**内，不会散落到别处。第 ⑨' 步额外在桌面
> 生成一个 `财报问答_交付物/` 副本夹，只为方便直接翻看——**真源始终是本仓库**，
> 改了原文件重跑一次即可同步，不要在副本里直接改。

## 全流程要跑多久

在本机（Windows 11，CPU 嵌入）**从零跑完约 20–25 分钟**，其中一多半花在向量嵌入上：

| 步骤 | 时间 | 来源 |
|---|---|---|
| ⓪ 预下载嵌入模型 | 12 秒 | 实测（走 `hf-mirror.com`） |
| ① 下载 15 份年报（约 46 MB） | 约 2–5 分钟 | **估计**，取决于网速；`download.py` 会跳过已存在文件，所以没法在不删 PDF 的前提下实测 |
| ② 解析 4,186 页 | **233 秒**（56 ms/页） | 实测 |
| ③' 表格审计 | 数秒 | 实测 |
| ④ 切块 11,313 块 | **1 秒** | 实测 |
| ⑤ 建索引 | **约 11.5 分钟**（BM25 12.1 s + 向量 657.3 s） | 实测 |
| ⑥⑦⑧ 评测 + 判分 + 报告 | 约 1–2 分钟 | 估计（10 次 LLM 调用，实测单次约 2 s） |
| ⑨ 截 8 张图 | 约 2 分钟 | 实测（含 4 次 LLM 生成） |

**瓶颈是 CPU 上的向量嵌入（657 秒，占一半以上）**，不是解析也不是生成。
解析只要 56 ms/页——所以"换个更快的 PDF 引擎"不是优先项；
真要提速，方向是减小嵌入批量/换更小的模型，或上 GPU。

若只是**复现代码而不重建索引**（例如改页面、改检索逻辑后看效果），
只需第 ⑨⑩ 步，**数十秒**即可。

## 页面

- `/` 检索界面：关键词 + 公司/类型/检索方式过滤，结果卡片显示
  **公司 · 板块 · 章节 · 页码 · 正文/表格 · 单位**，并附 `bm25#排名 / 向量#排名 / RRF 分`。
- 「生成答案」按钮：基于召回片段生成答案，句中 `[n]` 可点击跳回出处。
- `/eval` 评测总表。

检索功能**完全离线**，不需要任何凭证。只有"生成答案"需要 API。

## 技术选择及理由

| 选择 | 理由 |
|---|---|
| **fastembed + BGE-small-zh-v1.5（ONNX）** 做向量 | 约 115 MB，**不需要 torch**。Windows 上 torch 默认包约 2.5 GB，为这个任务装它是浪费。中文语义检索质量与 torch 路线接近。 |
| **pymupdf `find_tables()`** 做主表格引擎 | 实测 0.03 s/页；pdfplumber 约慢 30 倍，全量 4,186 页要跑近一小时。精度代价如实记录在 `docs/table_fidelity.md`，缺陷规模见 `docs/table_audit.md`。 |
| **RRF 融合** BM25 与向量 | 两路结果量纲不同，RRF 只用排名、不需要调权重，工程上更稳。 |
| **保留 `mode=bm25/dense/hybrid` 三种模式** | 评测里做消融，用来回答"融合到底有没有用、哪类题靠哪一路"。 |
| **`per_company_max` 配额 + `--fanout`** | 跨公司全景题的天敌：一次陈述可能占满整个 top-k，其余公司一个都进不来。两种策略都实现了，评测里对比。 |
| **Chrome/Edge 无头截图** | 本机已装 Chrome 151，`--headless=new --screenshot=` 直接出图，省掉 playwright 的 130 MB 下载。 |

## 几个踩过的坑（写下来省得再踩）

1. **巨潮的标题写法不统一**，只认「20XX年年度报告」会静默漏掉公司：
   中国神华写「2025**年度报告**」、中国石油写「2025**年年报**」、
   华能国际有「年度报告**全文**」后缀。必须放宽匹配。
2. **年报单位混用** 元/千元/万元/百万元。本方案把单位声明挂在表格元数据上并写进块的正文，
   让模型看见而不是猜——这是数值题答错的高发原因。
3. **BGE 中文模型的指令前缀只加在 query 侧**，passage 侧不加。
4. **深交所与上交所公司的年报标题格式不同**（上交所常带公司全称）。
5. **首次建向量索引时，fastembed 会「静默卡住」很久——不是死机，是在撞墙。**
   本机实测：`huggingface.co` 与 `cdn.qdrant.tech` 均超时（被墙），
   而该模型的两个源里，`url` 源指向 `storage.googleapis.com`（约 200 KB/s，能通但极慢），
   `hf` 源可走 `hf-mirror.com`。fastembed 先试哪个源不受我们控制，
   于是表现为「进程 CPU 在跑、但十几分钟不产出 `emb.npy`」。
   **解法是先用镜像把模型拉下来**，之后 fastembed 直接读缓存（实测加载 1.1 s）：

   ```bash
   HF_ENDPOINT=https://hf-mirror.com python -c \
     "from huggingface_hub import snapshot_download; snapshot_download('Qdrant/bge-small-zh-v1.5')"
   ```

   91 MB，走镜像约 12 秒。跑 `index_build.py` / `run_eval.py` / `shoot.py` 时带上
   `HF_ENDPOINT=https://hf-mirror.com`，并预留 **约 11 分钟**给 CPU 嵌入（11,313 块，实测 657 s）。
6. **`/eval` 页面曾因模板占位符没被替换而完全没有样式**（`render_template_string` 里写了
   `<style>__CSS__</style>` 却忘了传 `CSS=CSS`）。已修。凡是 `render_template_string` +
   字符串占位符混用的地方都容易出这个错——两套替换机制只生效一套。
7. **改完代码截图不变？先看端口上是不是挂着上一轮的旧服务。**
   Windows 下 Flask 开发服务器带 `SO_REUSEADDR`，**多个进程能同时绑上 5000 端口**，
   新进程绑得上却不接管流量，请求仍然被路由到先绑的那个旧进程。表现是：
   代码改了、服务端行为确实变了、截图却还是老的，而且**没有任何报错**。
   本机实测 5000 端口上曾同时挂着 **5 个**上一轮遗留的 `app.py` 进程，
   我在旧代码上截了一整组图才发觉。（`taskkill` 那些进程被权限策略拦了，
   于是改成不依赖清理的修法，见下条——这反而更稳。）
   现在 `shoot.py` **自己向系统要一个空闲端口**（`free_port()`），并且启动后断言
   应答的确实是本次进程（带 `?per_company_max=1` 请求首页，控件里必须出现
   `value="1" selected`）。**不校验的话，整组截图可能来自旧代码而过程毫无提示。**
8. **8 张截图不能共用同一个 Chrome `--user-data-dir`。** 共用时 Chrome 会把上一页的
   表单状态（下拉框选中项）恢复到下一页，**盖掉 HTML 里的 `selected` 属性**。
   后果是截图自相矛盾：`?per_company_max=1` 的页面服务端确实按配额检索了
   （写着"召回 6 块"），下拉框却显示"不限制每公司"——读者会以为配额没生效。
   每张图一个独立 profile 即可（`shot()` 里建、截完即删）。

| 3 | 8 张截图共用一个 Chrome profile，**下拉框状态被串页覆盖**，截图自相矛盾 | 交付物误导 | 已修，见坑 8 |

| 5 | README 称单位"挂在表格元数据上"，**实际只有 30.7% 的表格块带单位** | 文档高估 | 改为实测计数，见「已知局限」 |
| 6 | "表格还原有损"是**没法核对的定性说法** | 文档空泛 | 新增 `src/table_audit.py`，给出可复现计数 |

顺带记两条**差点误判**的：

- Q7 的证据在原文里是「桶油主要成**\n**本」——PDF 在**词中间**插了硬换行，
  精确子串匹配会把它判成"未召回"。**凡是对 PDF 文本做关键词/正则匹配的地方，
  都要先归一化空白**，否则证据召回率会被系统性低估。
- 想用 `n_col <= 1` 当"表格坍缩"的判据，实测**该判据命中 0 张**——真实的坍缩形态是
  "列数看着正常、内容全挤进第一个格子"。**指标选错比没有指标更危险**：它会让人
  理直气壮地得出"没问题"。

还有一条**没有修的**，如实留在上面"已知局限"里：单位缺失 69.1%。它可修（扩大
「单位：」声明的识别窗口），但属于解析层的改动，本轮不动它——**留着比假装没有好**。

## 已知局限

先说清楚**不要用「表格还原有损」这种没法核对的说法**——下面是实测计数，
由 `python src/table_audit.py` 生成、落到 `docs/table_audit.md`，可复现：

| 判据 | 实测（4,743 张表） |
|---|---|
| 坍缩表（单个单元格里聚 ≥8 个数值） | **131 张 / 2.8%** |
| 超长单元格（>60 字，多列并一格） | 482 张 / 10.2% |
| 列数异常（>20 列） | 50 张 / 1.1% |
| 单位缺失 | 3,278 张 / **69.1%** |

- **「坍缩」不是「表变成一列」**：`n_col <= 1` 的表有 **0** 张。真实形态是「列数看着正常、
  内容全挤进第一个格子」——601088 第 303 页的表 2，`n_row=3 n_col=2` 看着没毛病，
  实际一格里塞了 18 个数，列名与数值的对应关系全被拍平。**用列数当判据会完全漏掉它。**
  同一年报第 21 页的表还原得完全正确（6 列对齐）——同一份 PDF 里两种命运。
- **单位覆盖率比表面上低**：表格块 4,845 个，其中带 `unit` 元数据的只有 **1,485 个（30.7%）**。
  也就是说约三分之二的表格块，模型看到「332.1」时并不能从块本身得知这是百万吨还是吨。
  这是 R6（口径误读）的结构性来源，**主要该怪解析，不该怪模型不听话**。
- 表格还原的更细对照见 `docs/table_fidelity.md`（pymupdf vs pdfplumber）。
- 单次检索式 RAG 无法可靠回答需要**跨全库聚合**的问题（如"15 家里哪些净利润下滑"）。
  这是架构层面的限制，`--fanout` 只能部分缓解。详见 `REPORT.md`。
- 只覆盖 FY2025 单期，不支持跨期同比的自动计算（同比数据需年报本身披露）。
